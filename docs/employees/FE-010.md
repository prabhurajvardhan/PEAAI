## Mission

Own the **PEAAI frontend application architecture + production build infrastructure**.

Establish the correct production frontend architecture so that Vercel (and any equivalent
host) can reliably build and deploy PEAAI **without breaking the modular engineering
architecture** (the AD-010 module-local-config convention).

This is **not** "make Vercel green by any means." It is "establish the correct production
frontend architecture" — a real root application shell + a real production build pipeline —
while preserving the existing modular ownership of every feature module.

---

## Why This Task Exists

During the first Vercel deployment test, Vercel ran `npm run build` → `tsc`, and the
production build failed with a large number of TypeScript errors. The Vercel deployment
was building the `feature/ui-005-conversation-engine` branch.

Verified root-cause facts (CA inspection of the repository on 2026-08-15/16):

- Root `package.json` has `"build": "tsc"` and provides **no root Vite production build**.
- Root `tsconfig.json` has `"include": ["src/**/*.ts"]` and **does not configure JSX**
  (no `"jsx"` field). It also emits (`outDir`, `declaration`, etc.).
- There is **no root application entrypoint** confirmed: no root `index.html`, no root
  `vite.config.*`, no `src/main.tsx`, no `src/App.tsx`. The only app shell lives at
  **`src/app/`** (created by UI-009: `src/app/main.tsx`, `src/app/App.tsx`,
  `src/app/index.html`, `src/app/package.json`, `src/app/tsconfig.json`).
- Because the root `tsc` includes `src/**/*.ts` with no JSX, it attempts to type-check
  large portions of the modular frontend and produces errors from unrelated modules.
  CA count on current main: **129 errors across 10 module trees**
  (`conversation` 62, `app` 53, `layouts` 47, `foundation` 34, `components` 27,
  `transition` 11, `companion` 10, `pages` 8, `integration` 3, `graphics` 1).
- Most of these are **build-configuration errors** (JSX not set, CSS/`?raw` imports,
  vitest-config modules) — **not** genuine module defects. Some may be genuine defects
  belonging to individual module owners. FE-010 must **distinguish these categories**
  and must NOT silently "fix" code in modules it does not own.

Additional conflict discovered: `vercel.json` declares `VITE_API_URL`, but the actual API
client (PR #32, `src/services/api-config.ts`) reads **`VITE_API_BASE_URL`** (host only;
the client appends `/api/v1` itself). FE-010 must reconcile this so the deployed frontend
resolves the backend correctly.

## Repository Context (verified by the CA at assignment time)

- The repository is a **TypeScript modular monorepo** under `src/`. Frontend is **React 18**.
- The app shell exists at `src/app/` (UI-009): real React (`ReactDOM.createRoot`,
  `StrictMode`, `ThemeProvider`, `ToastProvider`, `ErrorBoundary`, `AppProviders`). Its
  `main.tsx` imports `../foundation/design-system/styles/variables.css` and `./styles/global.css`.
  Its `App.tsx` currently renders a placeholder `<main>` and notes "Routes and pages will be
  integrated by UI-004."

  `vitest.config.ts` (+ `tsconfig.json`) and is tested in isolation by the
  `frontend-module-tests` CI matrix. Root `tsc`/jest is intentionally minimal/diagnostic.

  configuration (JSX/css) rather than genuine code defects.

## Architecture Rules

1. **Do not redesign PEAAI architecture.** Establish the production build; do not change
   the modular ownership model.
2. **Reuse existing PEAAI components.** Do NOT generate a generic Vite template. Do NOT
   rewrite existing UI. Do NOT duplicate existing pages/components. Do NOT move modules
   without architectural justification.
3. **Preserve UI-005's and UI-009's work.** Integrate with their existing implementation
   rather than replacing it. **If FE-010 discovers an architectural conflict with
   UI-005/UI-009: STOP and report the conflict to the CA.** Do not silently rewrite their
   modules.
4. **Preserve the AD-010 module-local-config convention.** Module-local `vitest.config.ts` /
   `package.json` / `tsconfig.json` must remain isolated and functional. The root build must
   not absorb or break them.
5. **Clean separation between production build and TypeScript validation** — do not weaken
   type safety to make the build pass. If `tsc` type-checking is still required, run it as a
   distinct step with a correctly-scoped config, separate from the Vite production build.
6. **Environment variables only for deployment-specific config.** Do not hardcode staging or
   production URLs. Use `VITE_API_BASE_URL` (host only; the client appends `/api/v1`).
7. **Never commit secrets.** No AWS/Bedrock credentials, database credentials, JWT secrets,
   Render secrets, or private tokens in any file. Secrets belong in the Vercel/Render
   dashboard, not the repo.
8. **Do not modify another employee's module to fix an unrelated issue.** Document and report
   it instead (see category B above).
9. Follow existing `MODULES.md` ownership rules and `INTERFACES.md` contracts.

## Step-by-Step Implementation Guide

1. **Audit.** Run `npx tsc --noEmit` from the root and capture the full error list. Classify
   each error as (A) root-build-config or (B) genuine-module-defect. Record category-B items
   for the CA; do not touch them.
2. **Confirm architecture.** Confirm React + Vite is the intended production architecture
   (the app shell at `src/app/` is React 18 + `@vitejs/plugin-react`; this strongly indicates
   Vite). Document the decision and rationale in the PR.
3. **Establish the root entry.** Establish the root `index.html`, `src/main.tsx`, `src/App.tsx`
   (or point Vite at `src/app/index.html` + `src/app/main.tsx` if that is the deliberate,
   documented choice). Reuse UI-009's shell content; do not invent a generic template.
4. **Add root `vite.config.ts`.** Configure `@vitejs/plugin-react`, the correct `root`/build
   `outDir`, and any path aliases matching the module-local convention (e.g. `@/*`).
5. **Correct root `package.json` `build`.** Change `"build": "tsc"` to a Vite production
   build (`vite build`), and add any required root devDeps (`vite`, `@vitejs/plugin-react`).
   Keep the existing jest config and devDeps intact. If a separate type-check step is desired,
   add a `build:check` / `typecheck` script with a correctly-scoped config.
6. **Correct root `tsconfig.json`.** Add JSX config, set `noEmit` (Vite emits; tsc should
   not), and narrow `include` to the application entry surface so production type-checking
   does not process unrelated modules. Do not broaden to weaken safety.
7. **Fix `vercel.json`.** Use `VITE_API_BASE_URL` (not `VITE_API_URL`). Remove the broken
   `your-backend.onrender.com` `/api` rewrite — the frontend calls the backend directly via
   `VITE_API_BASE_URL` and the client appends `/api/v1`. Do NOT put `/api/v1` in the env var.
8. **Compose pages.** Wire `App.tsx` to compose the existing Landing/Auth/Home pages and
   UI-009's integration layer — only to the extent needed for a runnable root app. Do not
   implement routing logic that belongs to UI-004; if routing is required and missing,
   document it and report to the CA.
9. **Verify module-local tests remain isolated.** Confirm `src/app`, `src/conversation`,
   `src/foundation`, `src/components/landing`, `src/integration` still run their own vitest
   configs unchanged.
10. **Update docs.** Update `docs/deployment/DEPLOYMENT.md` (Vercel build command, output dir,
    root directory, `VITE_API_BASE_URL`) and `docs/engineering/CI.md` (build pipeline).
11. **Do not merge.** Open the PR and stop. The CA reviews.
